# Edition architecture and SQLite decision

The application remains one Go modular monolith. Domain/app/jobs code consumes `storage.Repository`. `ManagedRepository` adds lifecycle/integrity/backup for entry points only. Linux server build selects `internal/storage/sqlite`; `lite` selects the compatible legacy store through the bbolt edition facade. The original bbolt implementation stays at its package path to preserve existing test/API compatibility. No duplicated domain or protocol tree exists.

Linux uses pinned `github.com/ncruces/go-sqlite3 v0.30.5`, its database/sql adapter and embedded SQLite WASM, running in Wazero without CGO. References: [driver documentation](https://pkg.go.dev/github.com/ncruces/go-sqlite3/driver), [source](https://github.com/ncruces/go-sqlite3). It retains upstream SQLite behavior while supporting CGO-free amd64/arm64 cross-builds. Versions/checksums are in go.mod/go.sum. This is an implementation selection, not a claim that the chosen pinned version is the latest.

A CGO driver such as mattn/go-sqlite3 provides direct native SQLite with a C toolchain/platform linker requirement. A native implementation may reduce WASM runtime overhead; no apples-to-apples size/throughput benchmark was performed. modernc.org/sqlite is another pure-Go option with a translated SQLite implementation and its own dependency/size/maintenance tradeoffs; its downloads were rejected by the available proxy during implementation. ncruces was obtainable and avoids C cross-compilers; costs include embedded WASM, Wazero runtime/JIT/startup overhead and a larger Linux build. Lite excludes all of these dependencies. Artifact sizes are measurements of these builds, not driver-comparison evidence.

Schema migration 0→1 is transactional; unknown existing versions are refused. `collections` plus `records` hold every original encrypted JSON domain value under `(collection,id)`, preserving unknown collections and model fields. AES-256-GCM uses the original `collection:id` associated data and external 32-byte key. Nonces are freshly generated on import; ciphertext therefore changes while decrypted record values remain equal. No plaintext credential/profile/RouterOS secret is projected into SQLite indexes. `unique_name` holds a SHA-256 username digest for account uniqueness (equality leakage is intentional). `record_references` projects router/server/user/account references with composite foreign keys; target indexes support referential checks. Ownership/certificate/job payloads remain encrypted. Historical audit targets/job actors and router-held resource IDs are historical/external identifiers, not strict foreign keys.

One application instance per database remains the supported deployment model. In-process Update callbacks are serialized and transactional on one connection; busy_timeout=5000 and foreign_keys=ON are installed for every opened driver connection. WAL with synchronous=FULL is used on local Linux filesystems. Atomic single-record updates preserve delivery consumption/job persistence semantics; there is no new cross-record transaction API or multi-instance coordinator. SQLite enforces projected foreign keys and unique usernames in addition to the shared repository contract.

`Check` runs integrity_check/foreign_key_check and decrypts every payload. [SQLite VACUUM INTO](https://www.sqlite.org/lang_vacuum.html) creates consistent backups including committed WAL content; interrupted output is not trusted. CLI backups sync the output and verify it through private restore rehearsal. Restore copies only a completed backup to a private file, validates schema/key/all encrypted payloads, closes/checkpoints, and publishes via an atomic no-replace hard link. Original existing destinations are never overwritten by the database tool. Restrictive directory/file ownership is applied by the native installer.

The migration source is locked read-only and backed up using the original Store.Backup transaction mechanism. All original collections/IDs and canonical JSON values are compared after import, total counts are checked, relationships are enforced, and the SQLite staging copy is validated before activation. Unknown schemas, orphan references, duplicate accounts, bad keys and pre-existing destination/backup paths abort. No migration runs implicitly at server startup. See the operational migration runbook.
